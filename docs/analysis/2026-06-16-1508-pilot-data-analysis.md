# 파일럿 실험 데이터 분석 — GlanceShift vs. 베이스라인 메뉴

> 작성 2026-06-16. 원자료: `app/data/` (실험 로그 `pilot_P01_*.csv` 10개 + 설문 2개).
> 산출 요약표: 같은 폴더(`docs/analysis/`)의 `summary_trial_by_condition.csv`,
> `summary_survey.csv`. 비교 조건은 **GlanceShift(시선+머리)** vs. **베이스라인(Gamepad/키보드 메뉴)**.

---

## 1. 데이터 구성

### 1-1. 행동 로그 (`pilot_P01_*.csv`)
- 참가자 **P01 단일**(파일럿), 세션 10회 × 6 trial = **총 60 trial**.
- 각 세션 = `mouse-menu`(베이스라인, run1, 3 trial) → `glanceshift`(run2, 3 trial). 조건 순서 고정.
- 미션: 랜덤 타깃(game/voice/master)을 지정 방향(up/down)으로 목표량(Δ0.2)만큼 조절. 게임은 멈추지 않음.
- 조건별 30 trial.

### 1-2. 체감 설문 (Likert 1–7)
4문항: ① 통제감(↑좋음) ② 자연스러움/수월함(↑좋음) ③ 플레이 흐름 끊김(↓좋음) ④ 재사용 의향(↑좋음).
- **설문 1**: 한 조건이 끝날 때마다 따로 제출 → 행마다 조건 라벨이 있음. 8행(Gamepad/GlanceShift 교대)
  = **참가자 4명**이 두 조건을 각각 평가한 것으로 묶음.
- **설문 2**: 한 응답에 두 조건이 함께 담김(앞 4문항=1번째=베이스라인, 뒤 4문항=2번째=GlanceShift).
  7행 = **참가자 7명**.
- 합산 시 조건별 **n=11** 평가(설문1 4 + 설문2 7).

## 2. 행동 로그 결과 (P01)

| 지표 | 베이스라인(mouse-menu) | GlanceShift |
|---|---|---|
| 성공률 | **93%** (28/30) | 80% (24/30) |
| 총 명령시간 median | 5,594 ms | **4,319 ms** |
| └ 선택(coarse) median | 2,680 ms | 2,126 ms |
| └ 값 조절(control) median | 3,177 ms | **1,834 ms** |
| 선택 중 시선이탈 median | 161 ms | 519 ms |
| 조절 중 시선이탈 median | 342 ms | **27 ms** |
| 총 충돌 median | 1 | 3 |

**해석**
1. **속도는 GlanceShift 우세** — 총 명령시간 중앙값이 약 23% 짧고, 차이의 대부분이 **값 조절 단계**(3.2s→1.8s)에서 발생. 선택 단계는 비슷.
2. **시선 부담 패턴이 정반대** — GlanceShift는 선택 단계에 시선이탈이 크지만 조절 단계에는 거의 화면에 머묾(median 27ms). 베이스라인은 그 반대. 머리 기울임 rate-control이 시선을 화면에 붙들어 두는 효과.
3. **정확도·안정성은 베이스라인 우세** — GlanceShift는 성공률이 낮고(80%) 게임 충돌·완료 지연이 큼. 속도와의 트레이드오프.
4. **실패가 한 곳에 집중** — 미완료 8건 중 **7건이 `voice` 타깃 + `up` 방향**. 위로 올리는 voice 조절이 공통 난점(나머지 1건은 추적 끊김). UI/매핑 점검 1순위.

## 3. 체감 설문 결과 (조건별 n=11)

> **Update (2026-06-23)**: 이 절은 평균만 본다. 항목별 **대응표본 t-검정 · Wilcoxon · 효과크기**는
> [2026-06-23-1753-pilot-paired-tests.md](2026-06-23-1753-pilot-paired-tests.md) 참조
> (재현: `npm run analyze:pilot`). 요지 — 4항목 모두 GlanceShift 방향이나 소표본이라 α=.05 유의는 없음,
> 효과크기는 통제감·재사용·흐름끊김이 중간(d_z≈0.5).

| 문항 (방향) | 베이스라인 | GlanceShift |
|---|---|---|
| 통제감 (↑좋음) | 4.00 | **5.27** |
| 자연스러움 (↑좋음) | 3.64 | **4.36** |
| 흐름 끊김 (↓좋음) | 4.55 | **3.27** |
| 재사용 의향 (↑좋음) | 3.27 | **4.82** |

**4문항 모두 GlanceShift가 더 우호적** — 특히 재사용 의향(3.27→4.82)과 통제감(4.00→5.27) 격차가 큼. 흐름 끊김도 더 적게 느낌.

### 자유응답에서 드러난 정성 신호
- **긍정**: "아주 잠깐만 시선을 돌리면 되고 플레이에 집중할 수 있어 훨씬 좋았다", "GlanceShift가 간단하다", "적응만 되면 멀티태스킹이 더 잘 될 것 같다", "두 번째(GlanceShift)가 더 좋았다 — 첫 번째가 너무 불편해서".
- **개선 요구 (반복 등장)**:
  - **시선 인식 정확도** — "정확도가 좋아지면 유용할 것 같다", "시선 인식이 잘 안 돼 불편".
  - **의도치 않은 시선 인식** — "위에서 아래로 내려오는 장애물을 피하느라 시선이 아래로 갈 때가 많은데, 그때 의도치 않은 인식이 발생. 어느 방향을 볼 때 액션할지 잘 조정하면 좋겠다." (게임 특성과 시선 트리거의 충돌 → 설계 시사점)
  - 베이스라인 쪽은 "키보드 레이아웃이 불편" 지적.

## 4. 종합

행동 데이터와 체감 설문이 **같은 방향**을 가리킴: GlanceShift는 **더 빠르고**(특히 값 조절), **시선을 화면에 더 붙들어 두며**, **주관적 선호·재사용 의향이 더 높다**. 대신 현재 **정확도/안정성**(성공률·충돌·의도치 않은 트리거)이 약점이며, 사용자도 정확도 개선과 시선 트리거 방향 조정을 일관되게 요구.

**다음 점검 후보**
1. `voice` + `up` 조절 실패 집중 원인(매핑/UI).
2. 게임 중 하향 시선과 시선 트리거 충돌 완화(트리거 방향/영역 재설계).
3. 시선 추정 정확도/추적 끊김 개선.

## 부록 A. 지표 설명 (용어 정의)

보조명령 1건의 흐름은 **프롬프트 등장 → 타깃 선택(coarse, 시선) → 값 조절(control, 머리 기울임) → 완료**
순서다. 아래 시간 지표는 이 단계 경계를 기준으로 계산된다 (소스: `PilotExperiment.tsx`, `pilot-config.ts`).

**시간 지표 (낮을수록 빠름)**
- **선택시간 `selection_time_ms`** — 명령 시작부터 목표 항목을 **지목 완료**(`targetSelectedAtMs`)할 때까지. "무엇을 조절할지 고르는" coarse 단계 시간.
- **값 조절시간 `control_time_ms`** — 목표 지목 후부터 **마지막 값 조절 입력**까지. 선택한 항목 값을 목표까지 "맞추는" 단계 시간.
- **총 명령시간 `total_command_time_ms`** — 명령 시작부터 조절 종료까지 = **선택 + 조절** 전체. 보조명령 하나를 끝내는 데 걸린 총 시간.

**성공/정확도**
- **성공률 `command_success`** — 값 변화량이 목표 방향으로 목표량 이상이면 성공. up은 `value_end − value_start ≥ +0.2`, down은 `≤ −0.2` (목표량 `PILOT_TARGET_DELTA = 0.2`). 미달이면 `incomplete`.
- **값 변화량 `value_delta`** — 슬라이더 값(0~1) 변화(`value_end − value_start`). 목표는 `target_delta = 0.2`.

**시선/주의 (시간은 누적 ms, 낮을수록 좋음)**
- **선택 중 시선이탈 `gaze_off_ms_during_selection`** — 선택 단계 동안 시선이 게임(중앙 플레이 영역) **밖에 머문** 누적 시간.
- **조절 중 시선이탈 `gaze_off_ms_during_adjustment`** — 조절 단계 동안 시선이 게임 밖에 머문 누적 시간.
- **명령 중 추적 끊김 `gaze_missing_ms_during_command`** — 명령 수행 동안 시선 **추적 자체가 끊긴**(데이터 미수신) 누적 시간. UI 이탈이 아니라 추정 실패.

**게임 통제 (낮을수록 좋음)**
- **명령 중 충돌 `collisions_5s`** — 프롬프트 직후 분석창(`PILOT_ANALYSIS_WINDOW_MS = 5초`) 안에 발생한 충돌 수. "보조명령을 수행하는 그 순간" 게임 통제가 무너진 정도 — **명령 단위 지표**.
- **분석창 속도손실 `speed_loss_area_5s`** — 같은 5초 창 동안 기준 속도 대비 속도가 떨어진 양의 적분(면적). 명령 때문에 게임이 얼마나 느려졌나.
- **총 충돌 `collisions_total`** — 그 60초 런 전체의 누적 충돌 수. **런 단위 지표**(CSV에서 같은 런의 3 trial 행에 동일 값 반복).

> 참고: `collisions_total`과 `finish_*`(완료 지연)는 런 단위 값이라 명령 수행 비교용으로는 약함.
> 명령 순간의 게임 통제는 `collisions_5s` / `speed_loss_area_5s`가 더 적합하다.
